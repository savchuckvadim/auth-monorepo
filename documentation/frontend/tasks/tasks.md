# Задачи Frontend

## Инструкция для новичков

### Основные принципы работы

1. **Новая страница = Nav item**
   - Если добавляется элемент на уровне навигации (nav) - это новая страница
   - Пример: "Лента" в меню → страница `/network/feeds`

2. **SSR для страниц**
   - Если возможно, всю верстку делать на SSR (Server-Side Rendering)
   - Использовать Next.js App Router для SSR компонентов

3. **Выбор модуля (FSD архитектура)**
   - Если не понимаешь, в какой модуль добавлять - добавляй в `features`
   - При рефакторинге можно растянуть на `entities`, `widgets` и т.д.
   - **Исключение**: Если модуль делает глобальные вещи (управляет тем, какие страницы меняются) - это `process` (большая редкость)

4. **Управление состоянием**
   - Пытайся управлять состоянием загрузки данных с помощью **TanStack Query** (React Query)
   - Если не получается - используй **Redux RTK**
   - Избегай локального состояния для данных с сервера

5. **Установка библиотек**
   - **Избегай** установки каких-либо библиотек
   - Только по согласованности с командой
   - Используй существующие библиотеки из проекта

6. **FSD архитектура**
   - Следовать принципам Feature-Sliced Design
   - Использовать существующие entities, features, widgets
   - Не создавать дублирующую функциональность

7. **Структура DAL-BLL-UI**
   - Следовать структуре **DAL (Data Access Layer) - BLL (Business Logic Layer) - UI (User Interface)**
   - **DAL**: слой доступа к данным (API вызовы)
   - **BLL**: слой бизнес-логики (обработка данных, валидация, трансформации)
   - **UI**: слой интерфейса (компоненты, отображение)
   - Разделять ответственность между слоями

8. **API через Orval**
   - API в DAL использовать **только через Orval** и типизацию с бекенда
   - Использовать генерируемый клиент из `@workspace/nest-api`
   - Не создавать собственные API вызовы без Orval
   - Все типы должны приходить с бекенда через генерацию

9. **Tailwind компоненты**
   - Компоненты должны быть **максимально разбитыми, атомизированными, зарефакторенными**
   - Избегать больших монолитных компонентов
   - Разбивать на маленькие переиспользуемые части
   - Использовать Tailwind для стилизации

10. **Экспорт и импорт через index**
    - Каждый `export` из модуля объявляется через `index.ts`
    - Точно так же импортируется в другие модули
    - Не импортировать напрямую из файлов, только через `index.ts`
    - Пример: `import { Component } from '@/modules/feature/Component'` (не `from './Component/Component.tsx'`)

11. **Документация проекта**
    - **Внимательно читать документацию проекта** перед началом работы
    - Изучать существующие примеры и паттерны
    - Следовать установленным соглашениям
    - При сомнениях - обращаться к документации

12. **Тестовое покрытие**
    - **Все что написано должно быть покрыто тестами**
    - Писать тесты для компонентов, хуков, утилит
    - Использовать существующие инструменты тестирования проекта
    - Стремиться к высокому покрытию кода тестами
    - Тесты должны быть частью процесса разработки, а не после

## Примечания

- Все задачи должны быть выполнены в соответствии с FSD архитектурой
- При работе с API использовать только генерируемый клиент из `@workspace/nest-api`
- Следовать принципам, описанным в [Архитектуре FSD](../docs/architecture.md)
- Тестировать на разных устройствах и браузерах
- Если задача связана с backend, проверять наличие соответствующей backend задачи в `documentation/backend/tasks/`
- Управление состоянием: предпочтительно TanStack Query, если не получается - Redux RTK
- Избегать установки новых библиотек без согласования
