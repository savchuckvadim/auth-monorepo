# E2EE и мессенджер — доработки и риски

Задачи и замечания по состоянию кода и документации (после внедрения Signal E2EE и mobile push). Не дублируют общий бэклог, а фиксируют **зазоры безопасности и паритета**.

## Безопасность и инфраструктура

1. **WebSocket-аутентификация**: `NotificationsGateway`, `CallsGateway` (и частично другие) всё ещё опираются на `userId` в query без JWT — риск подмены при доступе к сокету. Нужна привязка к токену/handshake, как для REST.

2. **Кеш plaintext на веб-клиенте**: в `messenger-e2ee.ts` задокументировано использование localStorage для UX-кеша расшифрованного текста — для высоких требований рассмотреть отключение, шифрование кеша или только session memory.

3. **Логирование**: убедиться, что ciphertext и push-токены не попадают в логи в production (политика для `MessagesGateway`, push-слоя).

4. **Push payload**: уведомления о сообщениях не должны содержать plaintext; для E2EE используются плейсхолдеры — периодически ревьюить новые типы событий.

5. **FCM / APNS учётные данные**: хранить только в секретах окружения; ротировать при утечке; для VoIP — отдельный topic и ключи, как в `ApnsVoipPushService`.

## Функциональные пробелы

6. **Групповые чаты + SIGNAL**: на фронте отправка заблокирована; backend при необходимости — sender keys / дизайн группового E2EE (отдельный эпик).

7. **LiveKit E2EE для медиа**: не связано с хранением сообщений; при продуктовой необходимости — клиентский `createE2EEKeyProvider` и согласование ключей между участниками.

8. **E2E-тесты**: сценарии multi-device, offline push, входящий звонок при убитом приложении (см. [чеклист звонков и push](../docs/calls-push-integration.md)).

9. **Orval**: после изменений OpenAPI — регенерация клиента в `packages/nest-api`.
