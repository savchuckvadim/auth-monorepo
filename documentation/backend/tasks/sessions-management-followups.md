# Sessions management — follow-ups

## 1. Access-токен остаётся валидным после revoke

После `DELETE /sessions/:id` у ревокнутого устройства в течение ≤15 минут (TTL access) всё ещё
работает `GET /me`, `GET /chats` и т.п. Это сознательный trade-off: чтобы ревок был
"мгновенным", нужен либо blacklist access-токенов в Redis (каждый запрос → проверка),
либо перевод на короткие access (≤1 мин). Оставлено как есть до реальной необходимости.

Возможные варианты реализации, если понадобится:

- Хранить в Redis `revoked:<userId>:<iat>` → проверять в `AccessTokenGuard`.
- Уменьшить TTL access до 1 минуты + агрессивный refresh.

## 2. Нет rate-limit на GET /sessions

Аутентифицированный пользователь может поллить список сессий сколько угодно. Не уязвимость, но
стоит добавить `@Throttle` (например, 30 req/min), когда в проекте появится общий throttler.

## 3. Список устройств не имеет человекочитаемого имени

UI показывает User-Agent сырым. Хорошо бы парсить (через `ua-parser-js`) и хранить красивое
`deviceName` (например, `Chrome on Windows`, `iPhone 15, iOS 17`). Либо давать пользователю
возможность переименовывать сессии.

## 4. Нет уведомлений о новых сессиях

После `login` с нового устройства хорошо бы слать пользователю email: "Новый вход с IP X,
устройства Y. Это были не вы? Нажмите на ссылку для ревока". Сейчас не реализовано.

## 5. Нет endpoint'a "revoke all except current"

Сервис умеет это делать (`revokeAllSessions(userId, exceptRefreshToken)`), но контроллер
всегда ревокает ВСЁ. Если UX потребует кнопки "Выйти со всех других устройств" —
добавить отдельный `DELETE /sessions?keepCurrent=true`.

## 6. Нет фильтра по устройству

Сейчас `GET /sessions` возвращает всё списком. Когда сессий у активного пользователя станет
много, стоит добавить `limit/offset` или фильтр по `deviceId`.
